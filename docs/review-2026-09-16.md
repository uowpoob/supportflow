# SupportFlow 项目体检（2026-09-16）

对照 `docs/design-v1.md`、`docs/plan-v1-days.md` 与实际代码逐文件核对的结果。
**本文件只提问题与建议，未改动任何代码。**

## 一句话结论

后端 693 行、7 张表结构与 ORM 完全一致、登录链路前后端已打通；
但**业务数据一条都没有、业务接口全是空壳、身份体系没建立**。
按 `design-v1.md` 的目录树算，第③步该产出的文件**大约一半还没写**。

## 一、结构缺口（该有但不存在）

### 1. 地基三件套（越晚补越贵）

| 文件 | 作用 | 为什么必须现在补 |
| --- | --- | --- |
| `core/clock.py` | 全局唯一时间源 `utcnow()` | 退款窗口 14 天的边界用例（B07 恰好 14×24h 通过 / B08 加 1 秒拒绝）**必须能冻结时钟**。`datetime.now()` 一旦散落各文件，这些用例就永远不稳定 |
| `core/errors.py` | 业务异常 + 到 HTTP 状态码的映射 | 让 `services/` **不 import FastAPI**，纯业务代码可脱离 HTTP 单测，也能被 Agent 的 tool 直接复用 |
| `core/actor.py` | `Actor(user_id, username, role)` | service 只认 Actor 不认 ORM `User`：避免 detached instance 与懒加载；将来换认证方式只改 `api/deps.py` |

`core/config.py` 还缺两个常量：`REFUND_WINDOW_HOURS`（退款窗口，现在无处配置）、`POLICY_VERSION`（政策版本，检索与评测要用）。

### 2. 数据层

- **`alembic/` 整个目录不存在**。7 张表是手工建的，**没有任何版本记录**：以后改一列没有依据，部署时也没法在容器里跑 `upgrade head`。
  → 不必重跑建表。正确做法：`alembic revision --autogenerate` 后**核对生成的 DDL 与库内实际结构是否一致**，再用 `alembic stamp head` 把库标记为已应用该版本。
- **`scripts/seed.py`（确定性业务种子）不存在**。现在的 `db/seed_users.py` 只管账号，**订单/商品/退款一条数据都没有**。
  → 这是 M1 走不通的直接原因：没有 A1001（29900 分）这类样本，任何业务用例都无从断言。
  → 种子必须接 `--base-time` 参数、所有时间按偏移算。**签收时间绝不能写死成日期**，否则今天绿的用例两周后全红。

### 3. 业务层（第③步主体，全缺）

```
services/orders.py      get_order_for_user / check_refund_eligibility
services/refunds.py     submit_refund_request / decide_refund
services/conversations.py
schemas/order.py        schemas/refund.py     schemas/conversation.py
api/deps.py             api/orders.py         api/refunds.py
tests/conftest.py       test_orders.py  test_refund_rules.py  test_refund_flow.py  test_permissions.py
```

### 4. 后面才要的（现在别动）

`agent/{state,graph,nodes,tools,prompts}`、`retrieval/*`、`scripts/evaluate.py`。
新依赖：`pymilvus`（未装）、`langgraph`（能 import 但只是传递依赖，Day 8 必须显式 `uv add`）。

## 二、现有文件的问题

### A 级｜会被利用，或会导致返工

**A1. `/admin/**` 与 `/customer/**` 零鉴权**

实测（`httpx` 直连 8000）：

```
/admin/orders           -> HTTP 200  {"code":"200","message":"ok","data":{}}
/customer/orders        -> HTTP 200  {"code":"200","message":"ok","data":{}}
/admin/refund_approvals -> HTTP 200  {"code":"200","message":"ok","data":{}}
```

任何人都能读订单表、调审批接口。更实际的问题是：**这几个接口现在没法往下写业务**——业务第一步就要知道"这个请求是谁"，而项目里还没有"身份"这个概念。

**A2. 没有会话机制，登录之后后端不记得你是谁**

- 前端靠 `sessionStorage` 存 `{id, username, role}`，**改一下就是管理员**。
- 前端 `web/src/api/auth.ts::fetchCurrentUser()` 调 `GET /api/me`，**后端根本没有这个接口**（死代码）。

**A3. 登录存在账号枚举的时序侧信道**（`services/login.py`）

`authenticate_user` 在用户不存在时**直接 `return None`，不跑哈希**。实测中位耗时：

| 场景 | HTTP | 耗时 |
| --- | --- | --- |
| 账号存在 + 密码错 | 401 | **200 ms** |
| 账号不存在 | 401 | **4 ms** |

响应体一模一样，但**50 倍的时间差**足以枚举出哪些用户名真实存在。
→ 建议：用户不存在时也拿一个常量 dummy 哈希跑一次 `verify_password`，把两条路径拉平。

**A4. `schemas/result.py` 的自造信封**

```python
class success(BaseModel):
    code: str = "200"
    message: str = "ok"
    data: dict = Field(default_factory=dict)
```

三个具体代价：

1. **`data: dict` 把结构抹平**——精心写的 `LoginResponse` 在 OpenAPI 里只剩"一个 object"，而本项目后面要靠文档与评测。
2. **同一个接口两种响应形状**：登录成功是 `{code,message,data}`，登录失败是 `{"detail": ...}`。前端 `client.ts` 不得不写 `unwrap()` + `parseError()` 两套解析。
3. `design-v1.md` 里**没有这个设计**，项目其余部分都是 FastAPI 原生风格。

→ 二选一：**删掉信封**（推荐，顺手能删掉前端 `unwrap` 分支），或改成泛型 `ApiResponse[T]` 且 `code` 与 HTTP 状态码保持一致。
→ 注意：这个决定会连带影响 `web/src/api/client.ts`。

### B 级｜接口契约与命名

**B1. 审批接口的对象选错了**

`POST /admin/deal_refund_approvals/{order_id}`——表里是 `refund_approvals.refund_request_id`。
一个订单可以先后有多条申请（拒绝后可重新申请，见 `active_order_id` 的生成列设计），
用 `order_id` 做路径参数会导致"到底批的是哪一条"说不清。
→ 改成 `refund_request_id` 或 `refund_no`。

**B2. 分页参数没有约束**：`limit: int = 10`，传 `-1` 或 `100000` 都收。加 `Query(ge=1, le=100)`。现在是空壳所以还看不出后果，但一旦接上真实查询就是全表泄漏。

**B3. 命名不统一**：`check_orders` / `list_refund_approvals` / `deal_refund_approvals`。
`deal_` 这个动词不说明是批准还是拒绝。建议 `list_orders` / `list_refund_requests` / `decide_refund_request`。

**B4. 业务接口都没有 `response_model`**，OpenAPI 里看不到返回结构。

**B5. `schemas/result.py` 类名小写**（`success` / `error`），PEP 8 要求类名 CapWords；`code: str = "200"` 用字符串存状态码。

**B6. `services/login.py` 收 `LoginRequest` 当参数**——services 层不该依赖 `schemas/`（接口层对象）。
否则 Agent 的 tool 想复用这个函数时，也得先造一个 `LoginRequest`。
→ 建议签名改成 `authenticate_user(db, username: str, password: str)`。

### C 级｜一致性小瑕疵

- **C1** `core/config.py`：`DEEPSEEK_API_KEY`、`LANGSMITH_API_KEY` 是明文 `str`，而 `DASHSCOPE_API_KEY` 用了 `SecretStr`。建议统一。
- **C2** `db/seed_users.py` **自己又实现了一遍 bcrypt**，没复用 `core/security.py`；且密码随机生成只打印一次，开发期不好用（建议加 `--password` 参数或固定演示口令）。
- **C3** `main.py` 没有 `lifespan`——`db/session.py` 的注释写着"应用关闭时释放连接池"，但实际没有 `engine.dispose()`。
- **C4** `agent/llm.py`：模块顶层构造 client（只构造不发请求，安全），但没有 `timeout` / `max_retries`；`init_chat_model` 的 `api_base` 参数名建议实测确认（部分 provider 只认 `base_url`）。
- **C5** 依赖冗余：`jinja2`、`itsdangerous`、`python-multipart`、`passlib` **四个包零引用**（已 grep 确认）。其中 **`passlib` 早已停止维护，与 bcrypt 5.x 有已知兼容告警**，而你直接用 bcrypt 就够了 → 建议删。
- **C6** 文档滞后（建议**改文档而不是改代码**）：
  - `design-v1.md` 3.1 写 `models/user.py`、`models/order.py` 分文件 + `core/enums.py`；实际是 `models/entities.py` + `models/enums.py`。
  - 该文档写 `db/session.py` 提供 `get_session`，实际叫 `get_db`。
  - 7 张表放在一个 `entities.py` 挺好，没必要拆。
- **C7** 测试只有 5 个，且**不 import 应用**——应用起不起来测试都全绿（`result.py` 那个 `data:dict=dict` 的坑就是这么溜过去的）。
  → 补一个不碰数据库的 `tests/test_app.py`：导入 `app` + `/health` 响应体 + OpenAPI 能生成 + 多传字段是否 422。四个断言就够。
